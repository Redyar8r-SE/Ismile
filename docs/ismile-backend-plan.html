iSmile 2026 · Project brief

Backend, database,
payments & launch plan

A practical build plan for turning the current iSmile website into a secure registration and ticketing system, with Pretix and bank payments.

Recommended architecture: keep the current frontend; use Django for the custom backend, PostgreSQL for its database, Pretix for ticket orders and capacity, and a protected dashboard for staff workflows.

Prepared 23 September 2026
Planning document · Decisions about banks and Pretix hosting require confirmation before implementation.

1. Current state and target

The website already has pages for registration, sponsorship, speakers, workshops, schedules, partners, and content editing. Registration collects personal information, professional or student ticket choice, university details, an optional student-ID image, and a FIB or FastPay choice. It supports English, Arabic, and Kurdish.

The critical gap: the registration page currently shows a success message and creates a reference in the browser, but it does not save an attendee, create an order, or collect payment. Sponsor enquiries currently open WhatsApp or email. The current content admin is useful, but its browser-only access fallback cannot protect attendee or payment information.

The release goal is a complete journey: submit information, review student eligibility where needed, reserve a ticket, pay through a supported bank, verify the result on the server, issue the ticket, and give staff a reliable view of every step.

Pretix should own ticket inventory and order state. Our database stores the custom information and references to Pretix records. If Pretix is self-hosted, it gets separate database credentials; the custom backend accesses it through its authenticated API.

4. Registration and payment flow

Form → server validation → student review (if required) → Pretix order and reservation → bank payment → server verification → Pretix ticket → staff dashboard
  1. The browser sends form data and the image to the backend. The backend validates fields, upload type and size, and saves a registration. It returns a server-generated reference.
  2. If a student needs approval, staff review the private document. On approval, the student can continue to purchase. The initial policy should avoid charging before approval.
  3. The backend creates or starts the Pretix order using current ticket price and availability. The browser never decides the authoritative price or whether an order is paid.
  4. The customer completes the provider flow. A browser redirect shows a pending status until the server verifies the payment with the provider or Pretix.
  5. Pretix issues the ticket only after verified payment. Webhooks trigger synchronization; the backend fetches current Pretix data through the authenticated API before updating its local view.
  6. A scheduled task checks unresolved records and reconciles them with Pretix and the bank. Failed email delivery must not invalidate a paid order.

Submission and payment operations need idempotency keys: repeating a request must not create another order or charge. The workflow must cover timeouts, repeated or delayed callbacks, expired reservations, cancellations, full or partial refunds where supported, and the customer closing the page.

5. Pretix and bank integration

Pretix manages orders and tickets; a bank or wallet processes money. A bank API alone does not guarantee a ready Pretix integration. For each provider, check whether a compatible Pretix payment plugin already exists. If not, assess whether the chosen Pretix hosting permits a custom plugin. Build and fully test one provider before adding another.

For every bank we need its current documentation, sandbox credentials, allowed currency, hosted payment or checkout flow, callback and verification rules, refund capabilities, and settlement reports. Keep API secrets on the server. Prefer the provider's hosted payment interface so iSmile does not handle card details or bank credentials.

Pretix documents both payment-provider plugins and webhooks. Its webhook documentation warns that notifications can be duplicated and their contents should be used only as a trigger to fetch current data through the authenticated API. This is the behavior our integration will implement.

6. Dashboard and daily operations

Use Pretix's own management screens for ticket operations. Build a protected Django staff dashboard for iSmile-specific work. Begin with Django admin for internal records and add focused custom screens for tasks that require a clearer workflow.

Define owner, registration, finance, content, and check-in roles. Enforce permissions on the server for every action. Record approvals, exports, refunds and important changes in an audit history. The current browser-only admin fallback must be removed or disconnected from private data in production.

7. Security, privacy and recovery

  • Require HTTPS, secure sessions, multi-factor authentication for staff, and rate limits for login and public forms.
  • Validate every field again on the server. Use safe file processing, file-size limits and real file-type checks.
  • Keep student documents private; issue short-lived access links only to authorized reviewers. Set retention and deletion rules.
  • Keep bank credentials, Pretix tokens and application secrets in server-side secret storage; keep them out of browser code and the repository.
  • Protect browser actions from forged requests. Keep logs free of passwords, payment secrets and unnecessary personal details.
  • Back up PostgreSQL and private files off the application server. Test a real restore. Monitor backup failures, payment mismatches and worker failures.

Collect only information that the event team actually needs. Confirm the purpose of age, gender and student-ID collection before launch. Limit staff access and decide how long each category of data is retained.

8. Domain and hosting

Buy the domain when its name and ownership are settled. Choose server capacity after confirming whether Pretix is hosted or self-hosted. A preferred setup serves the public site through a CDN, runs Django and workers on a Linux application server, uses managed PostgreSQL and private object storage, and keeps a separate staging environment.

A single VPS can work for a constrained budget, but it is a shared failure point. Keep off-server backups and separate staging. A provisional starting size for the custom backend, with database and Pretix hosted elsewhere, is 2–4 virtual CPUs and 4–8 GB RAM; actual sizing depends on peak demand and testing. Do not expose PostgreSQL or Redis publicly.

Budget for the domain, hosting, database, private storage, backups, email delivery, monitoring, Pretix costs if applicable, payment fees, and ongoing maintenance.

10. Decisions needed to finalize implementation

  1. Pretix: pretix.eu, another hosted service, or self-hosted? Provide the URL and version without credentials.
  2. Payments: confirm all banks and wallets, starting with FIB and FastPay if these remain the choices. Provide current API documentation links first, not live secrets.
  3. Scale: expected total attendees and expected simultaneous registrations at peak.
  4. Budget and deadline: monthly hosting budget, launch date, and who will maintain the server.
  5. Ticket policy: ticket prices and currency, workshop limits, refunds, and whether students need approval before paying.
First implementation milestone: complete one sandbox purchase through Pretix and one bank, including a verified order status. That result will settle the payment architecture and inform the final hosting choice.
