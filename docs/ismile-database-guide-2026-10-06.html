Database: MySQL / MariaDB, utf8mb4 (Kurdish and Arabic stored exactly as typed). Server: api.ismile.krd (currently in test mode).

1. The one rule above all

A person is registered only after the payment company confirms the exact amount — or the Owner gives a free ticket. An unpaid form is never a registration: it never appears in the registrations, the lists or the counts, and it is deleted automatically if nobody pays.

2. The journey of one registration

1 · Form sentWebsite or office phone call → row in checkouts (status open)
›
2 · Payment startedRow in payments; the server works out the amount
›
3 · Psoola confirmsSigned webhook, logged in webhook_log; amount must match exactly
›
4 · RegisteredRow in registrations + tickets (T26-00001…)
›
5 · EmailQueued in emails, sent within a minute, in English
Website registration
The form is kept for 24 hours while the person pays. They must tick “tickets are non-refundable” (saved as terms_accepted_at).
Phone registration (office)
Staff fill in the form; the caller gets a “Pay now” email. The link works for 7 days (Settings → pay link days). Staff cannot type a price: the server always uses the website prices.
Wrong amount or paid twice
The payment is marked mismatch or duplicate: no ticket, held for Finance, who mark it kept after review. iSmile does not refund.
Free ticket
Only the Owner can give one, and must write a reason (comp_reason). The ticket's source is complimentary with no payment.

3. Prices and money

ItemPriceWhere it is set
Professional ticket40,000 IQDWebsite file data/tickets.json (Site content › Ticket prices). api.ismile.krd copies it from ismile.krd every minute.
Student ticket30,000 IQD
Lunch day 1not set yet (0)
Lunch day 2not set yet (0)
  • Prices are not stored in the database; the amount for each payment is calculated by the server at the moment of paying and saved in payments.amount_expected.
  • A price of 0 means “not set”: nobody can pay for that item. A lunch with price 0 cannot be chosen.
  • Every price change is noticed within 5 minutes, written to the audit log and emailed to the Owner.
  • Money is always whole Iraqi dinars (no decimals). Workshop and sponsor money is recorded separately (sections 5).

4. Design rules the database enforces by itself

  1. Links are checked (foreign keys): no payment for a form that does not exist, no ticket without a registration, no action by an unknown staff member.
  2. Fixed lists (ENUM): status, ticket type, language, payment method… any other value is refused.
  3. Rules (CHECK): e.g. a “paid” payment must have the exact confirmed amount; a student must have a university; a free ticket needs a reason; age 16–120.
  4. Unique: one ticket per person, one ticket per payment, each reference once, each Psoola payment recorded once, one booking per person per workshop.
  5. History is kept: registrations, payments and tickets are marked (cancelled, removed, disabled), not deleted. Staff accounts are disabled, never deleted.
  6. Text: utf8mb4 everywhere, so Kurdish and Arabic names are stored exactly as typed.
  7. Times: Asia/Baghdad local time, set by the server.

Sign-in protection
  • Passwords are stored only as a hash (never the password itself).
  • Phone codes (two-step sign-in): required for Owner and Finance; other roles may switch them on, and then they are always checked. Each code works only once.
  • 5 wrong passwords → account locked for 15 minutes, and the Owner is emailed. At most 20 sign-in tries per 15 minutes from one internet address.
  • Signed out after 30 minutes without activity, and after 12 hours at most. Changing a password or resetting the phone signs out every old session.

7. Emails

  • Every email is in English only. There is no setting or column for another language (removed 6 Oct 2026).
  • Kinds: ticket (registration confirmed), pay_now (phone registration payment link), sponsor_received (to the company), sponsor_notify (to the team), alert (to the Owner).
  • The text is written at sending time from the current data, so a resend after fixing an email address or name is correct.
  • If sending fails it is retried after 5, 15 and 40 minutes, then marked failed (shown on Communications and the Dashboard).
  • Email test mode (Settings, ON by default): every email goes to one test address instead of the real people. Turn it off at launch.
  • QR code + PDF ticket in the email: switched off until the entrance check is decided (setting ticket_qr_in_email).
  • Sending service: Resend (address ismile.krd must be verified before launch).

13. Changing the database safely

  1. backend/database/schema.sql is always the complete, current design; a new database is built from it alone.
  2. A change to a database already in use also needs an upgrade file in backend/database/migrations/ (named with the date). The deploy runs each file once and records it in schema_migrations. Never edit a file after it was applied.
  3. Applied so far: 2026-10-06-emails-english-only.sql (removes the email language column and the old setting).
  4. Order: test site first → backup of the live database → deploy to live.

14. Backups and restore

  • Nightly full export of every table and list, gzip-compressed, kept 30 days; Owner can download from Admin › Backups.
  • Tested on 6 Oct 2026: restoring a backup gives back every table and list exactly, including ID photo bytes, Kurdish/Arabic text, original times and calculated fields (38 checks passed).
  • The Owner is alerted if no backup was made in 36 hours.
