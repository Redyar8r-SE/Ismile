1What a "backend" is, and the three new folders

Until now the website was only pages: the registration form could not save anything, so it sent people to WhatsApp. The backend is the part that runs on the server. It receives the form, saves it in a database, talks to Psoola for the money, makes tickets, sends emails, and gives you the admin to see and manage everything.

2A professional registers and pays

  1. They open register.html. The page first asks the server: is registration open, what are the prices, which lunch days are left? If closed, they see "Registration opens soon" instead of the form.
  2. They fill in the 3 steps (details, lunch, payment method: Visa, MasterCard, FIB or FastPay) and press the button.
  3. The server checks everything again (it never trusts the page): name, phone, email, allowed choices, capacity, spam trap, too many tries.
  4. It saves the registration with a reference like ISM26-CB4TNZ and works out the price itself (ticket + chosen lunch days) from the prices in the admin.
  5. It asks Psoola to create a payment for exactly that amount and sends the visitor to Psoola's payment page.
  6. The visitor pays. Psoola sends them back to our new payment.html, which shows "Checking your payment…".
  7. Psoola also sends our server a message (webhook). Our server does not believe the message: it asks Psoola directly "is payment X paid, and how much?"
  8. Only if Psoola says paid, the right amount, the right currency: the registration becomes paid and a ticket is made (T26-00001, T26-00002…).
  9. The page changes to "You are in! Welcome to iSmile 2026" with the QR code, and the ticket email with the PDF goes out.

3A student registers

  1. Same form, but they choose "dental student", add their university, and upload a photo of their student ID. (Choosing "student" always gives the student ticket, whatever else they pick.)
  2. The photo is checked: must really be an image (a renamed program is refused), is re-saved clean, and stored in a private folder under a random name.
  3. No payment yet. They get the email "we are checking your student ID".
  4. Someone with the Registration role opens Student approvals in the admin, sees the photo large, and presses Approve or Reject with a reason.
  5. Approved → they get a "Pay now" email with a personal link → they pay the student price → ticket.
  6. Rejected → they get the reason and a link to student-id.html to send a clearer photo → it comes back to the approvals list.
Why approve first? So nobody pays and then needs a refund because their ID was not valid. Refunds are the messiest part of any payment system.

4Psoola: how payments are connected

There are exactly three connections with Psoola. All the code around them is finished; only the three places where we speak Psoola's "language" wait for their documents.

ConnectionWhat it doesState
ACreate a paymentOur server tells Psoola: "payment for ISM26-…, amount X IQD" and gets back the address of Psoola's payment page.needs Psoola docs
BWebhook (Psoola → us)Psoola tells us "payment X changed". Our server checks Psoola's signature on the message, writes it in the log, and then uses C. The message itself never makes a ticket.needs Psoola docs
CCheck a payment (us → Psoola)Our server asks Psoola: "what is the status and amount of payment X?" This answer is the only thing that can make a ticket.needs Psoola docs

Until Psoola's documents arrive, a pretend Psoola runs on the test site (api/fake-psoola.php). It shows a page where the tester chooses what happens: pay, fail, pay a smaller amount, pay but lose the webhook, or close the page. That is how every situation below was tested. The pretend Psoola refuses to run on the real address.

12The PDF ticket and the QR code

  • The ticket is a one-page A4 PDF in the person's language: name, ticket type, lunch days, reference, ticket number and a large QR code.
  • The QR code contains the ticket number plus a signature made with the server's secret. At the door, the check-in page verifies the signature: a QR made by someone else is refused as forged.
  • If a name is changed, the ticket becomes version 2 and is emailed again; the old QR stops working.
  • A second scan shows "Already checked in at …", so a copied ticket cannot bring two people in.

15Safety and security

Money

  • No ticket without Psoola itself confirming paid + exact amount + currency.
  • The server sets the price; the page cannot change it.
  • Each Psoola payment can be confirmed only once (the database locks the row while deciding).
  • Price 0 cannot be paid.
  • Fake webhooks refused and logged.

Visitors' data

  • Personal links cannot be guessed and expire.
  • ID photos: checked, cleaned, private, deleted after the summit.
  • Everything typed is stored as plain text: code or "SQL" in a name does nothing.
  • Spam trap + limits on how often one address can send forms.
  • Forms posted from other websites are refused.

Admin

  • Own account per person, 5 roles, checked on the server.
  • Phone code for Owner and Finance; lock after 5 wrong tries.
  • Sign-out after 30 minutes idle, 12 hours at most.
  • Every button has a one-time token (stops trick links clicking for you).
  • Admin pages cannot be shown inside another website.
  • Every action and every export in the audit log.

Server

  • The backend folder sits outside the public website.
  • Always HTTPS (padlock); internal files blocked even if uploaded by mistake.
  • Nightly backup; alerts if it is missing.

16Putting it on the server

  1. Two copies: test.ismile.krd (password-protected, pretend Psoola, emails in test mode) and ismile.krd (the real one). Always test first.
  2. deploy.sh: one command puts the project on the server: the website into the public folder, the backend outside it. cPanel's "Deploy" button runs it for the test site (.cpanel.yml).
  3. merge-data.php: an update never overwrites what you changed in the admin (prices, speakers, texts). It only adds new files and new translation texts.
  4. install.php: creates the 13 tables and your first Owner account.
  5. .htaccess files: HTTPS always, no "www", backend/docs/tools blocked, admin pages never cached.
  6. Cron jobs in cPanel for the timed jobs (section 13).
  7. Run the 88 checks on the test copy on the real server, then go live.

The step-by-step commands are in backend/README.md. I tested the deploy on a pretend server folder on this laptop: 14 new files and 454 new texts were added, and a price changed in the admin was kept.

18The security review and the fixes

After building, a second independent check read all the code looking for ways to break it. It confirmed the main rules hold (tickets only after confirmed money, locks against double payment, private photos, prepared database queries, escaped output, protected exports). It found 6 real problems. All are fixed and each now has a check that proves it:

#ProblemFix
1A trick sign-in link could send an admin to a fake site after signing in.Only our own admin pages are accepted as the next page.
2Paid after a declined card → money taken, no ticket.A late "paid" is always checked with Psoola and honoured.
3A failing link could send "Pay now" emails endlessly.Max one a day; recent attempts reused.
4"Registration off" did not stop pay links.Off now stops every payment.
5Last places could be oversold when many pay at once.Places held while paying; Owner alerted if a limit is ever passed.
6A rejected student could be approved without a new photo.Only a waiting photo can be approved or rejected.
+Smaller items.Pretend Psoola refused on any non-test address; odd links no longer crash pages; photos over 16 megapixels refused; very large page numbers handled.
