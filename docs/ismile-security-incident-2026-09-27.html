Security incident · fixed · 27 September 2026

Private files were downloadable from ismile.krd

For about 1 hour 20 minutes on 27 September 2026, anyone who knew the address could download private files from the live website, including the file that holds the website's secret keys. The hole is closed. The keys still need to be changed.

In one line: the new website server gave out every file in its folder, and the secret keys were stored in that same folder.

2. How it happened

On 27 September a new setup was added to host the website on a VPS (commit 97c301b, "Add VPS deploy for ismile.krd"). Two parts of it were fine on their own, but not together:

  1. The secrets were placed inside the website folder. The deploy writes the .env file into the same folder as index.html.
  2. The website server gave out any file in that folder. The small Node.js server (server/static.mjs) only blocked addresses that tried to climb out of the folder (../). It had no rule against hidden files like .env, or against private folders like docs/.

So https://ismile.krd/.env pointed at a real file, and the server sent it. This is a common mistake with a hand-written server: ready-made servers such as nginx block hidden files by default, a home-made one only blocks what it is told to.

4. What we did to fix it

The change: the server now uses an allow-list. It serves only the website itself, and answers "not found" to everything else:

  • Allowed: the pages (index.html, register.html, workshops.html, sponsor.html, admin.html, payment.html), favicon.ico, robots.txt, and the folders assets/, css/, js/, data/.
  • Never allowed: anything starting with a dot (.env, .git, …), and every other file or folder (docs/, server/, netlify/, package.json, …).
  • A new automatic test tries to download .env, the documents, the code and tricky encoded addresses, and checks that every one is refused.

How it reached the live site: the fix was pushed to the main branch on GitHub; the existing pipeline (.github/workflows/deploy.yml) deployed it to the VPS automatically. Nothing else changed on the website.

5. What still has to be done

The hole is closed, but the old secrets must be treated as known, because they were public for over an hour.
  1. Revoke the GitHub token and create a new one (GitHub → Settings → Developer settings → Personal access tokens). Then check the repository's recent activity for anything unexpected.
  2. Change the admin password and the session secret in the deploy settings (DEPLOY_ENV), and redeploy.
  3. Delete any downloaded copy of the .env file (for example in a Downloads folder).
  4. Pull before working on main, so the fix is not overwritten by an older copy.
  5. Lasting protection (recommended): keep .env outside the public folder, or put nginx in front of the Node server, so a single mistake in the code can never expose secrets again.
Lesson: secrets must never live in a folder that the website serves, and a web server should only give out an explicit list of public files.
