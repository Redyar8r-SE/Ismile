How the iSmile website is built

Everything in one place: the programming languages, the pages, the folders, how English, Arabic and Kurdish work, how the admin saves, and what the backend will add. Written from the real project files.

1The whole picture today

Today the site is plain files. It shows content, but it cannot store anything a visitor sends. Registrations and sponsor requests go out by WhatsApp or email. The backend (sections 10 and 11) adds a server and a database.

No framework. The site uses no React, no WordPress, no build step. The files you see are the files the browser gets. That keeps it fast, cheap and easy for any web developer to pick up. Fonts: Schibsted Grotesk for Latin letters and Noto Kufi Arabic for Arabic and Kurdish, from Google Fonts.

3The pages

index.html · home

Top of page, About, Program, Workshops, Speakers, Sponsors, For companies, Registration card, Venue with map, footer. Sections are drawn from the data files.

register.html

3 steps: personal details → ticket, lunch and payment method (Visa, MasterCard, FIB, FastPay) → review. Student ID photo for students. Makes a reference like ISM26-XXXXXX.

workshops.html

Workshop list with seats left. Booked by phone only; the phone number is "will be announced soon".

sponsor.html

Sponsorship or booth request in steps. The finished request opens in WhatsApp or email, already written.

admin.html

Edits every text, list, photo and price in three languages, grouped by page. Sign-in with email and password.

Every page

Language switch EN / العربية / کوردی, light / dark switch, phone-friendly menu, a loading cover that never blocks the page.

Rule 1: content is apart from code. Changing a speaker, a price or a sentence means changing a JSON file, which the admin does for you. Nobody touches the code for that.
Rule 2: one file per job. Each page section has its own CSS file and its own JS file with the same name, e.g. css/sections/program.css and js/sections/program.js.
Rule 3: colours in one place. Every colour and font is a token in css/base/tokens.css, with a second set for dark mode.

5What happens when someone opens the site

6The three languages: English, Arabic, Kurdish

Content files hold all three languages side by side:
"en": "Opening ceremony"
"ar": "حفل الافتتاح"
"ku": "ئاهەنگی کردنەوە"
A plain text shows the same in every language.
Nothing breaks if a translation is missing. A key without Arabic or Kurdish falls back to English. To add a new text: English with a key in the HTML, then the same key in ar.json and ku.json, or type it in the admin.
Right-to-left. Arabic and Kurdish flip the whole layout (menu, arrows, form steps) and switch to the Noto Kufi Arabic font. Phone numbers, prices and the ISM26 reference stay left-to-right so they read correctly. A fourth language would need one new JSON file and one button.

7Light and dark

The site follows the visitor's phone setting until they press the switch; then their choice is remembered in their browser (js/components/theme.js). All colours come from the tokens in css/base/tokens.css, so dark mode is a second set of the same names, not a second design.

8The admin: how your edits reach the website

After the hosting is bought: server/admin.php (PHP, already written) replaces a, b and c. Save writes straight to the server and the change is live at once. No GitHub key in the browser any more.
Safety rule already in the codeWhy
The admin may only write inside data/ and assets/uploads/even a stolen login cannot change the code
Passwords are stored only as a PBKDF2 hashnobody can read a password back, not even from the file
Language files are merged, never replaceda save cannot delete texts that only the code uses
The admin fetches the latest from GitHub before savingtwo people saving cannot wipe out each other's work
Secrets (admin-config.php) are never committedlisted in .gitignore
Honest limit today: the password screen on GitHub Pages is checked in the browser, so a skilled person can get past it. That is why the GitHub key is a stopgap, and why moving to your own hosting with admin.php is step one of the backend.

9Keeping visitors on the newest version

Browsers keep old CSS and JavaScript. Every file is loaded with a version number, for example main.js?v=74. After any change in css/ or js/, node tools/bump-version.mjs raises the number everywhere, so every visitor gets the new files together and never a broken mix.
